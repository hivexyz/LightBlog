# 机器达尔文内容计划书

## 1. 站点定位

机器达尔文是一个面向算法工程师和 AI 系统实践者的个人技术站。

它不只记录模型、框架和工具的使用方法，更关注 AI 系统如何在真实约束中演化：数据如何被选择，模型如何被约束，流程如何被验证，工程系统如何支撑长期迭代。

核心问题：

> 什么样的 AI 系统，能够在真实世界里持续进化？

## 2. 目标读者

主要读者：

- 算法工程师
- AI 应用工程师
- LLM / Agent / RAG 方向实践者
- 对 AI 工程化、评测、数据治理感兴趣的技术读者

次要读者：

- AI 产品经理
- 技术管理者
- 正在从传统算法转向大模型应用的工程师

读者期待的内容不是新闻摘要，而是具体问题、真实约束、工程取舍和可复用经验。

## 3. 内容原则

写作时尽量遵循：

- 少写口号，多写过程。
- 少写“最佳实践”，多写适用条件。
- 少写绝对判断，多写权衡。
- 少写工具堆砌，多写问题拆解。
- 每篇文章最好回答一个明确问题。
- 尽量从真实案例、实验、排查或系统设计出发。

每篇文章建议包含：

- 背景：为什么这个问题值得写。
- 问题：具体卡在哪里。
- 分析：涉及哪些技术、数据、工程或业务约束。
- 方案：尝试过什么，为什么这样选。
- 结论：哪些经验可以复用，哪些地方仍不确定。

## 4. 分类规划

### 大模型

关注大语言模型的原理、训练、微调、推理、评测与应用落地，记录从模型能力到系统能力的演化过程。

适合内容：

- Prompt 与上下文设计
- 模型能力边界
- 微调与 SFT 数据
- 推理成本与延迟
- 多模态模型观察
- 模型升级与迁移经验

### Agent

记录智能体系统的工具调用、任务规划、记忆机制、多轮交互与工程实现，关注 Agent 从 Demo 到可用系统的关键问题。

适合内容：

- 工具调用可靠性
- 任务规划与反思
- Agent 记忆机制
- 多步任务失败模式
- Workflow 与 Agent 的边界
- Agent 评测与线上监控

### RAG

围绕检索增强生成、知识库、向量检索、重排序、上下文构造与评测方法，沉淀可落地的知识增强实践。

适合内容：

- 文档切分
- Embedding 与向量库
- BM25 / Hybrid Search
- Rerank
- 上下文压缩
- 幻觉控制
- RAG 评测

### 模型评测

关注评测集、指标、错误分析、线上反馈和模型选择。评测不是为了给模型打分，而是为了指导系统迭代。

适合内容：

- Benchmark 的局限
- 自建评测集
- 错误案例分析
- 多模型对比
- 线上反馈闭环
- 人工标注一致性

### 数据治理

关注数据清洗、标注、质量控制、安全审核与训练数据构造。数据不是原料，而是系统演化中的选择压力。

适合内容：

- 数据清洗流程
- 标注规范
- 数据分层与抽样
- SFT 数据构造
- 内容安全审核
- 数据质量评估

### 工程实践

整理 AI 系统开发、服务部署、数据管线、监控排障、性能优化与工程取舍，关注模型如何稳定运行在线上。

适合内容：

- 服务部署
- 异步任务
- 日志与监控
- 成本优化
- 线上事故复盘
- 低资源部署
- 工程架构设计

### 行业观察

观察 AI 产品、技术趋势、开源生态与产业变化，分析新技术如何被选择、放大、淘汰或沉淀为基础设施。

适合内容：

- AI 产品趋势
- 开源框架观察
- 技术路线比较
- 商业化路径
- 开发者工具生态
- 模型平台变化

## 5. 标签体系

标签不需要一次性建太多，可以随着文章增长逐步增加。

第一批建议标签：

- AI系统
- 大模型
- Prompt
- Agent
- RAG
- Embedding
- 向量数据库
- 重排序
- 知识库
- 模型评测
- 数据治理
- 内容安全
- 工程实践
- 模型部署
- 监控排障
- 多模态
- 微调
- SFT
- 线上反馈
- 成本优化

标签原则：

- 标签表达具体技术点。
- 一篇文章可使用 3-6 个标签。
- 不要把分类名和标签完全重复太多。
- 当某个标签下文章超过 5 篇，可以考虑升级为分类。

## 6. 第一阶段内容目标

第一阶段目标不是追求数量，而是建立站点调性。

建议周期：4-6 周。

目标文章数：8-12 篇。

重点：

- 先写清楚站点为什么存在。
- 建立几个核心主题：AI 系统、RAG、Agent、评测、工程化。
- 每篇文章尽量形成可长期引用的基础观点。

## 7. 推荐首批文章

### 1. 机器达尔文：为什么我要记录 AI 系统的进化

分类：行业观察

标签：AI系统、大模型、工程实践、模型评测、机器达尔文

定位：开站文章，解释站点名称、关注方向和写作方式。

核心问题：

> AI 系统为什么不是一次性设计出来的，而是在数据、反馈和工程约束中被选择出来的？

### 2. 从 Prompt 到系统：为什么 LLM 应用的核心不是模型调用

分类：大模型

标签：Prompt、AI系统、工程实践、上下文

核心问题：

> 为什么很多 LLM 应用 Demo 很快，但真正上线很难？

要点：

- 模型调用只是最小环节。
- 真正复杂的是上下文、数据、评测、反馈和异常处理。
- Prompt Engineer、Context Engineer、Harness Engineer 的演化。

### 3. RAG 的第一性问题：到底在检索什么？

分类：RAG

标签：RAG、知识库、Embedding、向量数据库、评测

核心问题：

> RAG 系统失败时，问题通常不是“模型不够强”，而是“检索对象没有被正确定义”。

要点：

- 检索文档、段落、事实、答案、证据的区别。
- 文档切分不是格式问题，而是语义边界问题。
- RAG 评测应覆盖召回、引用和答案质量。

### 4. Agent 为什么容易停留在 Demo 阶段？

分类：Agent

标签：Agent、工具调用、任务规划、评测、工程实践

核心问题：

> Agent 从演示到生产，中间缺的是什么？

要点：

- 工具调用不可控。
- 多步任务错误会累积。
- 记忆和状态管理很难验证。
- Workflow 与 Agent 的边界。

### 5. 模型评测不是打分，而是构造选择压力

分类：模型评测

标签：模型评测、数据集、错误分析、线上反馈

核心问题：

> 为什么只看 Benchmark 无法指导真实系统迭代？

要点：

- Benchmark 是静态快照。
- 真实系统需要面向错误分布的评测。
- 评测集应来自线上失败案例和关键业务约束。

### 6. 数据清洗为什么决定了模型上限

分类：数据治理

标签：数据治理、SFT、内容安全、标注规范

核心问题：

> 为什么同样的模型和训练方法，数据不同会导致完全不同的系统行为？

要点：

- 数据清洗是规则、价值观和任务边界的显式化。
- 标注规范比标注工具更重要。
- 数据质量问题会在模型输出里被放大。

### 7. 一个 AI 系统上线前应该检查什么？

分类：工程实践

标签：模型部署、监控排障、成本优化、线上反馈

核心问题：

> 从实验到上线，AI 系统最容易漏掉哪些检查项？

要点：

- 输入输出边界。
- 超时、重试、降级。
- 日志与可观测性。
- 成本与限流。
- 灰度和回滚。

### 8. RAG、Wiki 与长期记忆：三种知识系统的差异

分类：RAG

标签：RAG、知识库、长期记忆、AI系统

核心问题：

> 运行时检索、持久化知识页和用户长期记忆分别解决什么问题？

要点：

- RAG 是运行时检索。
- Wiki 是知识编译与沉淀。
- Memory 是个体化状态。
- 三者可组合，但不能混为一谈。

### 9. 大模型应用里的成本，不只是 Token 成本

分类：工程实践

标签：成本优化、模型部署、上下文、RAG

核心问题：

> 为什么只看 token price 会低估 LLM 应用成本？

要点：

- 延迟成本。
- 失败重试成本。
- 上下文膨胀。
- 评测和人工标注成本。
- 运维和排障成本。

### 10. 开源 Agent 框架为什么很难直接落地？

分类：行业观察

标签：Agent、开源生态、工程实践、AI系统

核心问题：

> 为什么框架降低了搭建门槛，却没有自动解决系统可靠性？

要点：

- 框架解决抽象，不解决场景。
- 默认示例偏演示，生产需要约束。
- 选框架应看调试、状态、评测和可观测性。

## 8. 写作节奏

建议节奏：

- 每周 1 篇长文。
- 每 2 周 1 篇短观察。
- 每月做一次主题复盘。

第一月建议：

1. 开站文章。
2. LLM 应用为什么不只是模型调用。
3. RAG 的第一性问题。
4. Agent 为什么容易停留在 Demo 阶段。

第二月建议：

1. 模型评测。
2. 数据治理。
3. AI 系统上线检查。
4. RAG / Wiki / Memory 对比。

## 9. 单篇文章模板

```markdown
# 标题

## 背景

为什么这个问题值得讨论？

## 问题

具体问题是什么？它在什么场景下出现？

## 常见误区

哪些看似合理的做法会失败？

## 分析

从模型、数据、系统、工程、评测等角度拆开看。

## 方案或判断

我会怎么处理？为什么？

## 适用边界

这个方案在哪些条件下成立？哪些地方不适用？

## 小结

留下 3-5 个可复用结论。
```

## 10. 选题判断标准

一个选题值得写，最好满足其中至少两项：

- 它来自真实问题，而不是单纯追热点。
- 它能沉淀一个长期视角。
- 它能解释一个常见误区。
- 它能连接模型能力和工程落地。
- 它能形成后续文章的基础概念。

暂时不优先写：

- 纯新闻转述。
- 只复述论文摘要。
- 只罗列工具 API。
- 没有自己判断的框架测评。

## 11. 长期内容主线

机器达尔文可以长期围绕三条主线展开：

### 能力如何出现

模型、数据、Prompt、工具、检索、上下文如何组合出能力。

### 能力如何被验证

评测、错误分析、线上反馈、用户行为如何判断能力是否可靠。

### 能力如何被保留

工程系统、成本、稳定性、维护性、组织流程如何决定一个方案能否长期存在。

这三条主线对应的核心表达是：

> AI 系统不是被一次性发明出来的，而是在真实约束中被不断选择出来的。
